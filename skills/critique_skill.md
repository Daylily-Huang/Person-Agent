# critique_skill.md

## 用途

检查输出、计划或想法的漏洞。

## 触发条件

- 当前 mode 需要批判审查能力。
- 用户请求明确包含 review、纠错、漏洞检查或风险分析。
- 另一 skill 或 quality gate 识别到需交叉审查。

## 审查维度

### 1. 事实审查
- 引用有来源吗？来源可信度如何？
- 数字/日期/名称准确吗？
- 是否混淆了相关性和因果性？
- 样本能支持结论吗？
- 是否有选择性举证（只列支持自己观点的证据）？
- 跨学科引用是否跨过了方法论的迁移边界？

### 2. 逻辑审查
- 前提是否成立？
- 推理链条是否有跳跃？
- 是否存在循环论证、稻草人或假两难？
- 是否把局部结论泛化为全局规律？
- 是否忽略了替代解释？

### 3. 执行审查
- 计划是否考虑了资源和时间约束？
- 关键假设是否被验证或标注为假设？
- 是否有应对失败或延误的备选方案？
- 是否有单点故障（一个人/一个环节出问题 = 整体失败）？
- 完成标准是否可验证？

### 4. 边界审查
- 是否符合当前 mode 的边界规则？
- 是否符合 `persona/SOUL.md`？
- 是否过度拟人化？
- 是否诱导依赖或制造排他关系？
- 是否有潜在伤害（情绪/经济/隐私）？

### 5. 完整度审查
- 用户的核心问题是否被回答？
- 是否有重要但没有被问到的相关问题？
- 是否需要建议下一步行动？

## 问题严重性分级

| 级别 | 定义 | 行动 |
|------|------|------|
| 🔴 阻塞性 | 事实错误 / 逻辑断裂 / 边界越界 | 必须修正后才能使用 |
| 🟡 重要 | 信息不完整 / 方法有局限 / 风险未被标注 | 建议修正或补充标注 |
| 🟢 建议性 | 可以更好但当前可用 / 风格或优化类 | 给出建议，不强制修改 |

## 常用审查方法

- **替身论证**：站在反对立场，看自己能否推翻原来的结论。
- **条件测试**：如果某个关键假设不成立，结论还能站稳吗？
- **极限推演**：把方案推到极端条件下（最乐观/最悲观），看是否仍合理。
- **陌生人测试**：如果对这个领域一无所知的人读你的输出，会不会产生误解？

## 输出格式

问题清单 + 风险等级 + 修正方案。

## 质量标准

- 审查必须基于事实和逻辑，不能基于个人偏好。
- 必须区分"我不同意"和"这是错的"。
- 每项审查必须附判断依据。
- 修正方案必须具体可操作。
- 审查对象不是用户本身，而是用户的输出/计划/想法。

## 禁止事项

- 不把 skill 当成人格本体。
- 不自动修改核心人格或长期记忆。
- 不编造用户信息。
- 不越过当前 mode 的边界。
- 不把审查变成人身攻击或贬低。
- 不为了显示批判能力而制造不存在的漏洞。
- 审查的是观点和计划，不是用户本人的能力或价值。
